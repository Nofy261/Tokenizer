1) Une blockchain est un registre partagé entre des milliers d'ordinateurs.On ne peut pas falsifier une transaction,
car chaque bloc est lié au précédent par un hash, et toutes les autres copies du registre contrediraient la modification.

2) L'adresse publique sert à recevoir des tokens et à m'identifier sur la blockchain. La clé privée sert à signer mes transactions,
c'est-à-dire à prouver que c'est bien moi qui les envoie. Celui qui possède la clé privée contrôle le compte.
Mes tokens sont enregistrés sur la blockchain, à mon adresse. Mon wallet garde ma clé privée et me permet de signer des transactions.
Le wallet, c'est une application, comme MetaMask, qui fait trois choses :
Il garde tes clés en sécurité. C'est le porte-clés : ton adresse publique et ta clé privée sont rangées dedans.
Il t'affiche ton solde. Il va lire dans le grand cahier, la blockchain, combien de tokens sont notés à ton adresse, puis il te les montre.
Il signe tes transactions. Quand tu veux envoyer des tokens, il utilise ta clé privée pour signer à ta place, sans que tu aies besoin de la manipuler toi-même.

3) Un smart contract est un programme deployé sur la blockchain, à une adresse precise, qui execute automatiquement
ses règles et ne peut pkus être modifié une fois en ligne.

4) - Un token(monnaie inventée) est un smart contract qui respecte un standard (BEP-20 sur BNB Chain), cad une liste de fonctions communes
qui permet à tous les wallets et explorers de le comprendre.

- Le standard BEP-20 c'est la liste des règles communes que tous les tokens respectent.- la blockchain est un registre public de toutes les transactions,
 que tout le monde peut consulter, mais où les personnes sont identifiées par des adresses et non par leur nom.


- La blockchain est un registre public où l'on voit toutes les transactions du réseau, identifiées par des adresses.
 Le smart contract est un programme déployé sur cette blockchain qui gère le token : il garde les soldes et applique les règles.
 Le token est la monnaie numérique que ce smart contract crée et qu'on peut s'échanger.

- Respecter le standard BEP-20 garantit la compatibilité de mon token: comme il implemente les mêmes fonctions
que tous les autres tokens, il est automatiquement reconnu par les wallets comme MetaMask, par les explorers comme 
BscScan et par ;es applications de l'écosysteme BNB Chain.

- MetaMask sert à agir sur la blockchain, BscScan sert à la consulter.

1. C'est quoi un smart contract ?
C'est un programme déployé sur la blockchain. Il a quelques particularités :

Une fois déployé, il a sa propre adresse (comme le wallet) et on ne peut plus modifier son code.
Il garde un état (des variables stockées sur la blockchain, par exemple qui possède combien de tokens).
Tout le monde peut appeler ses fonctions. Lire est gratuit. Écrire, c'est-à-dire modifier l'état, coûte du gas, payé en tBNB.
C'est à ça que servent les 0.01 tBNB.
Le code est public, donc n'importe qui peut chercher une faille. D'où l'importance de la sécurité.
BSC est compatible EVM (la même machine virtuelle qu'Ethereum). L'écrire en Solidity, comme sur Ethereum

2. C'est quoi un token BEP-20 ?
Un token n'est pas une pièce qui se déplace. C'est juste un smart contract qui contient un registre :

adresse A → 1000
adresse B → 250
« Envoyer des tokens », c'est appeler une fonction qui fait -50 sur A et +50 sur B dans ce registre.

BEP-20 (l'équivalent d'ERC-20 sur Ethereum) est un standard : une liste de fonctions que le contrat doit avoir.
Comme ça, MetaMask, BscScan et les exchanges savent tous comment lui parler.

3. Les briques Solidity à connaître
À retenir : mapping, msg.sender, constructor, require, modifier, event/emit.
Avec ça,on peut écrire un BEP-20.

4. La sécurité (!!!)

Qui est l'owner et quels pouvoirs a-t-il ?
Peut-on créer (mint) de nouveaux tokens après le déploiement ? Si oui, qui ? Supply fixe ou pas ?
Que se passe-t-il si quelqu'un envoie plus qu'il ne possède, ou envoie vers l'adresse 0x0 ?
Peut-on transférer ou renoncer à l'ownership ?

Version avec option Owner(celui qui deploie devient l'owner) et privilege
// SPDX-License-Identifier: MIT
// -> licence du code (MIT = tout le monde peut le réutiliser)
pragma solidity ^0.8.20;
// -> version de Solidity : 0.8.20 ou plus (minimum pour OpenZeppelin v5)

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
// -> toutes les fonctions BEP-20 (transfer, balanceOf, approve...)
import "@openzeppelin/contracts/token/ERC20/extensions/ERC20Pausable.sol";
// -> ajoute la possibilité de mettre le token "en pause" (bloquer tous les transferts)
import "@openzeppelin/contracts/access/Ownable.sol";
// -> ajoute la notion d'owner (propriétaire) et le modifier onlyOwner

// Le contrat hérite de 3 contrats OpenZeppelin :
// ERC20 = le token, ERC20Pausable = la pause, Ownable = l'owner
contract Nofy42TokenWithOwner is ERC20, ERC20Pausable, Ownable {

    // Exécuté une seule fois au déploiement
    // ERC20(...)          -> donne le nom et le ticker
    // Ownable(msg.sender) -> celui qui déploie devient l'OWNER (c'est la différence avec mon contrat)
    constructor() ERC20("Nofy42 Token", "NF42") Ownable(msg.sender) {
        // crée 1 million de NF42 (en miettes) et les donne à celui qui déploie
        _mint(msg.sender, 1_000_000 * 10 ** decimals());
    }

    // PRIVILÈGE 1 : créer des tokens quand on veut
    // "public"    -> tout le monde peut essayer de l'appeler de l'extérieur
    // "onlyOwner" -> mais seul l'owner passe, les autres sont refusés (OwnableUnauthorizedAccount)
    // C'est une "porte publique" vers _mint (qui est interne)
    // -> la supply n'est plus fixe : l'owner peut créer autant de NF42 qu'il veut
    function mint(address to, uint256 amount) public onlyOwner {
        _mint(to, amount);
    }

    // PRIVILÈGE 2 : bloquer TOUS les transferts de tout le monde
    // après pause(), tout transfer / transferFrom est refusé (EnforcedPause)
    function pause() public onlyOwner {
        _pause();
    }

    // débloque les transferts (seul l'owner peut le faire)
    function unpause() public onlyOwner {
        _unpause();
    }

    // Obligation technique (pas un privilège) :
    // _update est la fonction interne appelée à CHAQUE mouvement de tokens (transfer, mint...).
    // ERC20 et ERC20Pausable ont tous les deux une version de _update,
    // donc Solidity oblige à dire qu'on combine les deux (override(ERC20, ERC20Pausable)).
    // super._update(...) exécute les deux : la vérification "est-ce en pause ?" puis le transfert.
    function _update(address from, address to, uint256 value)
        internal
        override(ERC20, ERC20Pausable)
    {
        super._update(from, to, value);
    }
}

// RÉSUMÉ de la différence avec mon contrat (nofy42.sol) :
// - mon contrat : pas de Ownable, pas de Pausable, pas de fonction mint publique
//   -> pas d'owner, supply fixe, personne ne peut bloquer les transferts (même pas moi)
// - ce contrat : l'owner peut créer des tokens et bloquer tout le monde
//   -> les utilisateurs doivent faire confiance à l'owner

C'est quoi un « standard » BEP-20 ?
C'est une liste de règles que tous les tokens suivent pour que les wallets (MetaMask) et les sites (BscScan) sachent les lire. Une sorte de format commun, comme une prise électrique standard : n'importe quel appareil peut s'y brancher.

Ce standard exige que mon token sache faire quelques actions de base :
donner son nom, son symbole et son nombre de décimales ;
dire combien de tokens existent au total (totalSupply) ;
dire combien de tokens possède une adresse (balanceOf) ;
envoyer des tokens à quelqu'un (transfer) ;
autoriser quelqu'un à dépenser une partie de mes tokens (approve, allowance, transferFrom).

« Mon token est un ERC20 ». Ton contrat hérite de toutes les fonctions d'OpenZeppelin : transfer, balanceOf, etc. Tu n'as pas besoin de les écrire.

solidity
uint256 private constant INITIAL_SUPPLY = 1_000_000;

Le nombre total de tokens qui existeront : 1 million. constant veut dire que ce nombre ne peut jamais changer.

solidity
constructor() ERC20("Nofy42 Token", "NF42") {
    _mint(msg.sender, INITIAL_SUPPLY * 10 ** decimals());
}

Le constructeur s'exécute une seule fois, au moment du déploiement, puis plus jamais. Il donne le nom (« Nofy42 Token ») et le symbole (« NF42 »), puis il crée (_mint) le million de tokens et les donne à msg.sender, c'est-à-dire toi, l'adresse qui déploie.

Pourquoi 10 ** decimals() ?

Les blockchains ne connaissent pas les nombres à virgule. Pour pouvoir envoyer 0,5 NF42, on découpe chaque token en tout petits morceaux. Par défaut il y a 18 décimales, donc 1 NF42 = 1 000 000 000 000 000 000 petites unités (un 1 suivi de 18 zéros).

C'est comme les euros et les centimes : la banque compte en centimes pour éviter les virgules, sauf qu'ici il y a 18 « chiffres de centimes » au lieu de 2.

La partie sécurité (voir sujet!!!)

Le sujet dit de réfléchir à « ownership or privileges », c'est-à-dire : est-ce que quelqu'un a des pouvoirs spéciaux sur le token ? Dans ton contrat, personne n'en a :

Pas d'owner : aucune adresse n'est « chef » du contrat.
Pas de fonction mint publique : personne ne peut créer de nouveaux tokens après le déploiement. Le million est fixé pour toujours.
Pas de fonction pour bloquer ou confisquer : personne ne peut geler ou prendre les tokens de quelqu'un.

BONUS:

Créer un multisig, c'est-à-dire un système où plusieurs personnes doivent être d'accord avant qu'une transaction puisse partir. Le but est la sécurité : une seule personne ne peut pas tout faire seule. Le sujet te demande de choisir combien de signatures sont nécessaires et qui a le droit de signer, puis de l'adapter à ton token.

Ton choix : 3 owners, 2 signatures nécessaires (on dit « 2-of-3 »).

L'idée en une image
Un compte bancaire commun à 3 personnes, avec une règle : pour faire un virement, il faut la signature d'au moins 2 personnes sur 3. Si une personne perd sa carte ou se la fait voler, le voleur ne peut rien faire seul. Et si une personne est absente, les deux autres peuvent quand même agir.
Ton multisig, c'est ce compte commun, mais pour des NF42.

Le fonctionnement en 3 étapes
Toute sortie de NF42 du multisig passe obligatoirement par ces étapes :
Propose : un owner dit « je propose d'envoyer X NF42 à telle adresse ». Rien ne part encore.
Confirm : les owners donnent leur accord, un par un. Chaque owner ne peut confirmer qu'une seule fois.
Execute : quand il y a assez de confirmations (2), un owner déclenche l'envoi. Les NF42 partent.

Les variables : ce que le contrat retient


IERC20 public token;
-> L'adresse de ton token NF42. C'est ce qui relie le multisig à ton token : il ne gère que des NF42. 

address[] public owners;
mapping(address => bool) public isOwner;
-> La liste des 3 owners, plus une table qui permet de répondre vite à la question « cette adresse est-elle owner ? » (oui ou non).

uint256 public requiredConfirmations;
-> Le nombre de confirmations nécessaires : 2.

struct Transaction {
    address to;
    uint256 amount;
    uint256 confirmations;
    bool executed;
}
Transaction[] public transactions;
-> Une fiche pour chaque transaction proposée : à qui envoyer, combien, combien d'owners ont confirmé, et si elle a déjà été envoyée. Toutes les fiches sont rangées dans une liste, numérotées 0, 1, 2…

mapping(uint256 => mapping(address => bool)) public isConfirmed;
-> Une table qui retient, pour chaque transaction, quel owner a déjà confirmé. C'est elle qui empêche un owner de confirmer deux fois.

modifier onlyOwner() {
    require(isOwner[msg.sender], "Not an owner");
    _;
}
-> Un « videur » : les fonctions marquées onlyOwner refusent tous ceux qui ne sont pas dans la liste des owners. Un inconnu ne peut ni proposer, ni confirmer, ni exécuter.

Le constructeur
S'exécute une seule fois, au déploiement. Il reçoit l'adresse du token, la liste des owners et le nombre de confirmations.
Il vérifie que :
l'adresse du token n'est pas vide ;
il y a au moins un owner ;
le nombre de confirmations est entre 1 et le nombre d'owners (on ne peut pas demander 4 signatures avec 3 owners) ;
aucun owner n'est l'adresse 0 ni présent en double.

propose(to, amount)
-> Crée une nouvelle fiche avec 0 confirmation et executed = false, puis renvoie son numéro. Elle refuse l'adresse 0 et un montant de 0.

confirm(txId)
-> Vérifie que la transaction existe, qu'elle n'est pas déjà envoyée et que cet owner n'a pas déjà confirmé. Puis elle note la confirmation et ajoute 1 au compteur.

execute(txId)
-> Vérifie que la transaction existe, qu'elle n'est pas déjà envoyée et qu'il y a au moins 2 confirmations.

Puis:
transaction.executed = true;
require(token.transfer(transaction.to, transaction.amount), "Token transfer failed");
-> Elle marque d'abord la transaction comme envoyée, puis envoie les NF42 depuis le solde du multisig.

Les events:
TransactionProposed, TransactionConfirmed, TransactionExecuted : des annonces publiques qui apparaissent sur BscScan. Elles permettent à tout le monde de suivre l'historique.

La partie sécurité
Personne ne peut envoyer seul : il faut 2 confirmations sur 3.
Un owner ne peut pas confirmer deux fois pour atteindre le seuil tout seul.
Une transaction ne peut pas être exécutée deux fois grâce à executed.
Seuls les owners peuvent agir, grâce à onlyOwner.
executed = true avant l'envoi : c'est le pattern « checks-effects-interactions ». Si on mettait à jour après l'envoi, un contrat malveillant pourrait essayer de rappeler execute pendant l'envoi pour recevoir les tokens deux fois. En marquant d'abord, le deuxième appel est refusé.

Mon multisig est un coffre qui détient des NF42. Trois comptes sont autorisés à confirmer les transferts.
Deux confirmations de comptes différents sont nécessaires avant qu’un propriétaire puisse exécuter l’envoi.
Une personne seule ne peut donc pas sortir les tokens.

BONUS — Déroulement complet du coffre MultiSig

Principe : un coffre séparé détient des NF42. Trois comptes sont propriétaires
du coffre et deux confirmations de propriétaires différents sont nécessaires
pour faire sortir des tokens. Ils contrôlent le coffre, pas le contrat NF42.
Le multisig ne crée aucun token : il utilise les NF42 déjà créés dans le mandatory.

Les montants donnés aux fonctions sont en petites unités : 1 NF42 = 10^18 unités.

1) Déployer le coffre

Account 1 déploie MultiSig depuis Remix avec ces paramètres :
tokenAddress = adresse du contrat NF42 déjà déployé
ownersList = [adresse Account 1, adresse Account 2, adresse Account 3]
required = 2

Le constructeur vérifie que l'adresse du token n'est pas zéro, qu'il y a au
moins un propriétaire, que les propriétaires sont différents et non nuls,
et que le seuil est supérieur à zéro et ne dépasse pas leur nombre.
Le code permet plusieurs configurations : nous choisissons ici 2 sur 3.

Résultat : le coffre reçoit sa propre adresse et possède 0 NF42.
Account 1 paie le gas du déploiement en tBNB.

2) Déposer 50 NF42 dans le coffre

Avec Account 1, appeler sur le CONTRAT NF42 :
transfer(adresseDuMultisig, 50000000000000000000)

Le contrat NF42 vérifie notamment qu'Account 1 possède assez de tokens.
Account 1 perd 50 NF42 et le coffre reçoit 50 NF42.
Aucun approve n'est nécessaire : Account 1 envoie ses propres tokens.

3) Proposer d'envoyer 10 NF42 à Account 3

Avec Account 2, appeler sur le CONTRAT MULTISIG :
propose(adresseAccount3, 10000000000000000000)

Le multisig vérifie qu'Account 2 est propriétaire, que le destinataire n'est
pas l'adresse zéro et que le montant est supérieur à zéro.
Il enregistre une proposition avec :
to = adresse Account 3
amount = 10 NF42 en petites unités
confirmations = 0
executed = false

Aucun token ne bouge. Proposer ne compte pas comme confirmer.
La première proposition porte le numéro txId = 0 ; les suivantes : 1, 2, etc.
Pour la suite, utiliser le numéro réel de la proposition créée.

4) Donner le premier accord

Avec Account 1, appeler sur MultiSig :
confirm(0)

Le multisig vérifie qu'Account 1 est propriétaire, que la proposition existe,
qu'elle n'est pas exécutée et qu'Account 1 ne l'a pas déjà confirmée.
Résultat : une confirmation. Les 50 NF42 restent dans le coffre.

À ce stade, execute(0) serait refusé : il manque une confirmation.
Erreur attendue : Not enough confirmations.

5) Donner le deuxième accord

Avec Account 3, appeler sur MultiSig :
confirm(0)

Les mêmes vérifications sont effectuées pour Account 3.
Résultat : deux confirmations. Aucun token ne bouge encore : confirmer
n'exécute pas automatiquement le transfert.
Account 3 peut confirmer même s'il est le destinataire : le code l'autorise.
Account 2 aurait aussi pu confirmer sa propre proposition.

6) Exécuter le transfert

Avec Account 2, appeler sur MultiSig :
execute(0)

N'importe lequel des trois propriétaires aurait pu le faire.
Le multisig vérifie que l'appelant est propriétaire, que la proposition
existe, qu'elle n'a pas déjà été exécutée et qu'elle a au moins deux confirmations.

Il marque la proposition comme exécutée, puis appelle lui-même sur NF42 :
transfer(adresseAccount3, 10000000000000000000)

L'expéditeur des tokens est cette fois le coffre, car c'est lui qui appelle
transfer sur NF42. Le contrat NF42 vérifie son solde et effectue le transfert.
Le réseau BSC Testnet exécute ces programmes et leurs vérifications.

Si le transfert échoue, toute l'exécution est annulée, y compris le passage
de executed à true. La proposition peut être réessayée après avoir corrigé
la cause de l'échec, par exemple en déposant assez de NF42 dans le coffre.

7) Vérifier le résultat

Sur le CONTRAT NF42 :
balanceOf(adresseDuMultisig) = 40 NF42 en petites unités
balanceOf(adresseAccount3) = ancien solde + 10 NF42 en petites unités

Sur le CONTRAT MULTISIG :
transactions(0) : confirmations = 2 et executed = true

Une seconde tentative de execute(0) est refusée.
Une deuxième confirmation du même propriétaire est également refusée.

Gas : à chaque étape d'écriture, le compte qui signe paie le gas en tBNB.
Dans ce scénario, Account 1 paie le déploiement, le dépôt et sa confirmation.
Account 2 paie la proposition et l'exécution. Account 3 paie sa confirmation.
Le coffre n'a pas besoin de tBNB pour cet appel interne au contrat NF42 :
le gas de l'appel interne est couvert par la transaction d'exécution.

Dans BscScan, Read Contract permet de lire les soldes et les propositions.
Write Contract permet d'appeler propose, confirm ou execute avec le bon
compte connecté. Vérifier l'adresse connectée avant chaque opération.

Transaction[] public transactions =>
Je creer un tableau nommé transactions, dont chaque element sera uen fiche de type Transaction

Transaction définit le modèle d’une fiche de proposition.
transactions est le tableau qui range ces fiches.
transactions[0] est la première fiche, transactions[1] la deuxième, etc.

mapping(uint256 => mapping(address => bool)) public isConfirmed => une table à deux clés
isConfirmed[0][adresseOwner]
Cette table mémorise qui a confirmé chaque proposition, pour empêcher une même personne de confirmer deux fois
EX:
Proposition 0 → Account 1 → true  : il a confirmé
Proposition 0 → Account 2 → false : il n’a pas confirmé
Proposition 1 → Account 1 → false : il n’a pas confirmé celle-ci

Exemple : envoyer 100 NF42 du coffre à Account 3, avec 2 accords sur 3.
1. Account 1 propose → proposition 0 créée
   Account 1 → false
   Account 2 → false
   Account 3 → false
   confirmations = 0

En resumé le constucteur vérifie les parametres, puis enregistre le token, les proprietaires et le nombres de confirmations necessaires.

propose(): creer une demande(fiche) de transfert et renvoie son numero
Le premier appel réussi à propose() creer la fiche numero 0 et renvoie 0

confirm(): reçoit le numero d'une proposition. Elle verifie que l'appelant est proprietaire, que la proposition existe,
n'est pas executé et qu'il ne l'a pas deja confirmé. Puis enregistre son accord, augmente le compteur et emet un evenement.

execute() reçoit le numéro d’une proposition. Elle vérifie que l’appelant est propriétaire, que la proposition existe,
n’a pas déjà été exécutée et a assez de confirmations. Puis elle la marque exécutée, transfère les NF42 du coffre au destinataire et émet un événement.
Si le transfert échoue, toute l’opération est annulée.
